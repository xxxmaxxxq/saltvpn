# 🛡 Панель Marzban и выдача ключей

Этап, после которого бот начинает выдавать **настоящие рабочие ключи VPN**.
До него подписка создавалась в базе, но конфигов внутри не было — их некому
было генерировать.

---

## Что появится

| Компонент | Роль |
|---|---|
| **Marzban** | Панель: аккаунты Xray, ключи, ноды, статистика трафика |
| **Xray (ядро в Marzban)** | Принимает подключения клиентов по VLESS + Reality |
| **panel.ваш-домен** | Веб-интерфейс панели, только для вас |
| **vpn.ваш-домен** | Клиентская часть: подписки, импорт, Mini App |

Панель вынесена на **отдельный субдомен** намеренно: у Marzban свои пути
`/api/*`, и на одном домене они столкнулись бы с `/api/miniapp/*` сервиса.

---

## Про порт 8443

На мастер-сервере порт 443 занят Caddy — он обслуживает HTTPS для подписок
и Mini App. Поэтому VLESS слушает **8443**.

Это рабочий вариант, но со своей ценой: часть корпоративных и гостиничных
сетей выпускает наружу только 443. Когда появится отдельный сервер под ноду,
Reality переедет на 443 и этот минус исчезнет. Менять при этом придётся
одну строку — порт в конфиге ноды.

---

## Почему рядом с панелью работает маленький проброс

Marzban без SSL-сертификатов слушает только `127.0.0.1` — это его встроенное
поведение, а не ошибка: панель не хочет светиться в интернет без шифрования.
Но тогда до неё не достучаться и соседним контейнерам.

Выдавать панели самоподписанный сертификат ради внутренней связи — лишняя
сложность. Вместо этого рядом живёт контейнер `marzban-proxy` (socat) в том же
сетевом пространстве: он отдаёт localhost панели на порт 8080. Снаружи HTTPS
по-прежнему терминирует Caddy, а бот и API обращаются к `http://marzban:8080`.

## Развёртывание

### 1. Вторая A-запись

В панели регистратора добавьте ещё одну запись — на тот же IP:

| Тип | Субдомен | Значение |
|---|---|---|
| A | `panel` | IP мастер-сервера |

### 2. Настройки в `.env`

```bash
echo 'PANEL_BASE_URL=https://panel.ваш-домен' >> .env
echo 'MARZBAN_USERNAME=admin' >> .env
echo "MARZBAN_PASSWORD=$(openssl rand -hex 16)" >> .env
echo 'SERVICE_NAME=SaltVPN' >> .env
```

Пароль панели посмотрите потом в `.env` — он понадобится для входа.

### 3. Запуск

```bash
bash scripts/deploy-master.sh
```

Что делает скрипт:

1. проверяет обе A-записи и сверяет их с IP сервера;
2. собирает образы;
3. генерирует ключи Reality (X25519) — если ключи уже есть, **переиспользует**,
   иначе перевыпуск разорвал бы работающие подписки;
4. собирает конфиг Xray из шаблона и кладёт его в том панели **до** первого
   старта: без файла ядро Xray не поднимется;
5. поднимает Marzban, бота, API, воркеры и Caddy;
6. дожидается панели и прописывает ноду — и в саму панель (host: адрес, порт,
   SNI), и в базу сервиса (чтобы работали тарифы и Auto-Healing).

### 4. Проверка

```bash
bash scripts/deploy-master.sh status     # все контейнеры running
curl https://vpn.ваш-домен/health        # {"status":"ok",...}
```

Откройте `https://panel.ваш-домен`, войдите под `MARZBAN_USERNAME` и
`MARZBAN_PASSWORD`. В разделе Inbounds должен быть `VLESS_REALITY_nl-1`.

Затем в боте: `/start` → «🎁 Попробовать 3 дня бесплатно» → «⚡ Подключить
в 1 клик». Happ импортирует подписку, и внутри уже будет рабочий сервер.

## Вторая нода (российская)

### Про порт

Панель раздаёт **один конфиг Xray на все ноды**: каждый inbound поднимается
на каждой ноде. Поэтому порт для российской ноды должен быть свободен и на
мастере тоже — 443 там занят Caddy. Берём **2053**: он свободен на обоих
серверах и снаружи выглядит обычным HTTPS-портом.

К какой ноде пойдёт клиент, решает не inbound, а запись host в панели:
тариф «🇳🇱 Европа» отправляет на `<MASTER_HOST>:8443`, тариф «🇷🇺 Россия» —
на `<RU_NODE_HOST>:2053`.

### 0. Обновить код на мастере

```bash
cd ~/saltvpn/repo && git pull && cp -r dorabotki/vpn-service-project/. vpn-service-project/
cd vpn-service-project
```

Команды ниже пересоберут контейнеры сами: после `git pull` код на диске
новее, чем внутри работающего контейнера, и новых команд CLI там ещё нет.

### 1. Взять сертификат панели (на мастере)

```bash
bash scripts/deploy-master.sh node-cert
```

Скопируйте весь вывод, включая строки `-----BEGIN CERTIFICATE-----`
и `-----END CERTIFICATE-----`.

### 2. Поднять ноду (на российском сервере)

```bash
ssh root@<RU_NODE_HOST>
bash scripts/install-node.sh   # репозиторий приватный: файл берётся из клона, а не по ссылке
```

Записать сертификат (вставьте его вместо строки-заглушки):

```bash
cat > /var/lib/marzban-node/ssl_client_cert.pem <<'CERT'
-----BEGIN CERTIFICATE-----
...сертификат из node-cert...
-----END CERTIFICATE-----
CERT
```

Запустить:

```bash
bash /opt/marzban-node/start.sh
ufw allow 2053
```

`start.sh` поднимает ноду обычной командой `docker run`: плагина `compose`
в сборке Docker из репозитория Ubuntu нет, а ради одного контейнера ставить
его незачем. Перед запуском скрипт проверяет, что сертификат на месте и не
повреждён — иначе нода поднимется, но останется в статусе error.

Запускать ноду нужно именно через `start.sh`, а не голым `docker run`:
скрипт сначала снимает старый контейнер (`docker rm -f marzban-node`).
Без этого повторный запуск падает с
`Conflict. The container name "/marzban-node" is already in use`.

Скрипт `install-node.sh` ставит Docker, открывает порты (22, 443, 2053,
62050, 62051), включает BBR и сетевой тюнинг.

### 3. Подключить ноду (снова на мастере)

```bash
bash scripts/deploy-master.sh add-node ru-1 ru <RU_NODE_HOST> 2053 www.samsung.com
```

Одна команда делает четыре вещи: добавляет inbound в конфиг Xray
(ключи Reality для новой ноды генерируются, старые не трогаются),
обновляет конфиг в панели, регистрирует ноду и прописывает host
и запись в базе сервиса.

В конце она напомнит закрепить список нод, чтобы он не потерялся при
следующем полном развёртывании:

```bash
echo 'NODES="nl-1:8443:www.nvidia.com ru-1:2053:www.samsung.com"' >> .env
```

### 4. Подписи профилей в клиенте

В списке подписок Happ каждая локация подписана флагом и страной —
🇳🇱 Нидерланды и 🇷🇺 Россия. Логин аккаунта (`u<telegram_id>`) в подпись
не попадает: иначе на чужом телефоне был бы виден Telegram ID владельца.

Новые ноды получают такую подпись сразу, при `add-node`. Если нода была
заведена раньше — перепишите подписи разом:

```bash
bash scripts/deploy-master.sh relabel
```

### 5. Проверить

```bash
bash scripts/deploy-master.sh status
docker exec salt_api python -m app.cli doctor --telegram-id ВАШ_ID
```

В боте команда `/nodes` покажет обе ноды со статусом и задержкой. После
этого тариф «🇷🇺 Россия» начнёт выдавать ключи на российский сервер,
а «🌍 Мульти» — сразу на обе локации.

### Если нода не подключается

| Симптом | Причина |
|---|---|
| Статус `error` в панели | Сертификат вставлен не полностью или с лишними пробелами |
| Статус `connecting` дольше минуты | Закрыты порты 62050/62051 на ноде: `ufw allow 62050 && ufw allow 62051` |
| Нода `connected`, но ключи не работают | Не открыт 2053: `ufw allow 2053` на российском сервере |
| `PermissionError: /generated/reality-keys.json` | Старая версия скрипта: генератор конфига запускался от `appuser`, а `config/generated` принадлежит root. `git pull` — теперь `deploy-master.sh` запускает его с `--user root` |

## Кто подключён и у кого есть подписка

Команды в боте (доступны только тем, чей ID указан в `ADMIN_IDS`):

| Команда | Что показывает |
|---|---|
| `/users` | Подписчики: тариф, остаток дней, трафик, когда заходили последний раз |
| `/online` | Кто пользуется VPN прямо сейчас и из какого приложения |
| `/user <tg_id>` | Карточка человека: подписка, оплаты, слоты устройств |
| `/stats` | Сводка: люди, выручка, конверсия триала |

То же самое видно в панели: `https://panel.ваш-домен` → раздел Users.

### Почему в списке нет IP-адресов

В конфиге Xray стоит `access: none` — история подключений не пишется вообще.
Это осознанное решение: нет журнала, нет и предмета для изъятия, а
пользователю есть что предъявить в описании сервиса.

Ценой идёт то, что нельзя посмотреть, с каких адресов заходит человек, и
нельзя ограничивать устройства по числу одновременных IP на уровне ядра.
Если такая проверка понадобится (например, против массового шеринга ключей),
потребуется включить access-логи на нодах и поставить сборщик вроде
Marzban IP Limit. Это обратный размен: контроль в обмен на журнал
подключений, который придётся где-то хранить.

## Если ключ не выдаётся

Первым делом — диагностика. Она проходит весь путь выдачи и показывает,
на каком шаге он рвётся:

```bash
docker exec salt_api python -m app.cli doctor --telegram-id ВАШ_ID
```

Пример здорового вывода:

```
✓ Пользователь: tg=100200300, аккаунт u100200300
✓ Подписка: multi, trial, осталось 2 дн.
✓ Ноды под тариф: nl-1
✓ Панель отвечает, inbounds: {'vless': ['VLESS_REALITY_nl-1']}
✓ Аккаунт в панели: статус active, inbounds {'vless': ['VLESS_REALITY_nl-1']}
✓ Путь подписки в панели: /sub/eyJhbGciOiJIUzI1NiIsInR5cCI6...
✓ Конфиги: HTTP 200, длина 412
✓ Серверов в подписке: 1
    vless://c7e337fd-...@<MASTER_HOST>:8443?security=reality&sni=www.nvidia.com...
```

Где обычно рвётся:

| Строка с ✗ | Причина и что делать |
|---|---|
| Нет ноды под тариф | `python -m app.cli setup-marzban --host IP` |
| Панель недоступна | Панель не поднялась: `docker logs salt_marzban` |
| Аккаунта нет в панели | Создастся сам при проверке; если нет — смотрите ошибку выше |
| Серверов в подписке: 0 | В панели нет host для inbound: `setup-marzban` |

## Частые вопросы

**Ключ импортировался, но интернет не идёт.**
Проверьте, что порт 8443 открыт: `ufw allow 8443` на сервере. И что в панели
у пользователя статус `active`.

**В панели нет inbound VLESS_REALITY_nl-1.**
Значит конфиг Xray не доехал. Посмотрите логи панели:
`docker logs salt_marzban --tail 50` — там будет причина (чаще всего
невалидный JSON после ручной правки).

**Хочу сменить маскировочный домен.**
```bash
XRAY_SNI=www.samsung.com bash scripts/deploy-master.sh
```
Ключи при этом сохранятся, поменяется только SNI.

**Нужно всё пересоздать с нуля.**
```bash
bash scripts/deploy-master.sh stop
docker volume rm salt_marzban_data
rm -rf config/generated
bash scripts/deploy-master.sh
```
Осторожно: выданные ранее ключи перестанут работать.
