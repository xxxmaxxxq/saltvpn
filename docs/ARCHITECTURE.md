# 🏗 Архитектура сервиса

## 1. Общая схема

```
                         ┌──────────────────────────────────────┐
                         │          MASTER-СЕРВЕР (DE/FI)       │
 Пользователь            │                                      │
   Telegram ──────────►  │  ┌────────────┐   ┌───────────────┐  │
                         │  │ bot        │   │ api (FastAPI) │  │
                         │  │ aiogram 3  │   │ вебхуки,      │  │
                         │  └─────┬──────┘   │ /sub, MiniApp │  │
                         │        │          └───────┬───────┘  │
                         │        └────────┬─────────┘          │
                         │                 ▼                    │
                         │  ┌───────────┐  ┌───────┐  ┌──────┐  │
                         │  │PostgreSQL │  │ Redis │  │worker│  │
                         │  └───────────┘  └───────┘  └──────┘  │
                         │                 │                    │
                         │          ┌──────▼───────┐            │
                         │          │   Marzban    │            │
                         │          │   (панель)   │            │
                         │          └──────┬───────┘            │
                         └─────────────────┼────────────────────┘
                                           │ gRPC/REST (порт 62050/62051)
                        ┌──────────────────┴──────────────────┐
                        ▼                                     ▼
          ┌──────────────────────────┐        ┌──────────────────────────┐
          │  NODE NL 🇳🇱             │        │  NODE RU 🇷🇺             │
          │  Marzban-node + Xray     │        │  Marzban-node + Xray     │
          │  VLESS/Reality :443      │        │  VLESS/Reality :443      │
          │  Hysteria2    :443/udp   │        │  Hysteria2    :443/udp   │
          └──────────────────────────┘        └──────────────────────────┘
                        ▲                                     ▲
                        └────────── трафик пользователя ──────┘
```

**Главный принцип:** пользовательский трафик никогда не идёт через мастер.
Мастер — это «мозг» (биллинг и управление), ноды — «мышцы» (пропуск трафика).
Поэтому блокировка ноды не роняет бота, а падение мастера не обрывает уже
подключённых пользователей.

## 2. Компоненты

| Компонент | Технология | Ответственность |
|---|---|---|
| `bot` | aiogram 3 | Диалог с пользователем, кнопки, deep links, админ-команды |
| `api` | FastAPI + uvicorn | Вебхуки платежей, Mini App API, редирект `/sub/{token}` |
| `worker` | asyncio + APScheduler | Уведомления, списание дней, Auto-Healing, разморозка пауз |
| `postgres` | PostgreSQL 16 | Единственный источник правды по деньгам и подпискам |
| `redis` | Redis 7 | FSM aiogram, кэш профилей, rate-limit, антифрод-метки |
| `marzban` | Marzban | Управление Xray-нодами, генерация конфигов и подписок |
| `caddy` | Caddy 2 | HTTPS-терминация, автосертификаты, reverse-proxy |

Бот, API и воркер — **один Python-пакет** `apps/api-server/app` с общими моделями и
сервисами, но три разных процесса (три контейнера). Это даёт переиспользование
кода без общего состояния в памяти.

## 3. Поток данных: покупка подписки

```
1. Пользователь жмёт «Купить · Мульти · 3 мес»
2. bot → services.billing.create_order()  → payments(pending) в БД
3. bot → payments.platega.create_invoice() → ссылка на оплату
4. Пользователь платит на стороне Platega
5. Platega → POST /webhook/platega  (api)
6. api проверяет HMAC-подпись и идемпотентность по external_id
7. services.subscriptions.extend()  → +90 дней (+streak-бонус)
8. services.marzban.sync_user()     → продление/создание в Marzban
9. services.referrals.on_first_payment() → начисление слота рефереру
10. bot отправляет пользователю ключ + deep link + чек
```

Всё, что касается денег, выполняется **в одной транзакции БД**; обращение к
Marzban — после коммита, с ретраями (если Marzban недоступен, задача попадает в
очередь `retry_sync` в Redis и повторяется воркером).

## 4. Модель подписки и ключа

Один пользователь = **один аккаунт в Marzban** = **одна ссылка-подписка**, которая
не меняется никогда. Смена тарифа/локации = изменение набора `inbounds` у этого
аккаунта. Отсюда следуют два важных свойства:

- **Dynamic Subscription:** меняем ноды/протоколы на бэкенде → клиент получает новые
  конфиги при очередном обновлении подписки, ключ перевыпускать не нужно.
- **Auto-Healing работает прозрачно:** пользователь даже не узнаёт, что нода сменилась.

Имя пользователя в Marzban: `u<telegram_id>` (например `u123456789`).

## 5. Auto-Healing: алгоритм

```
каждые 120 с для каждой ноды:
    ok = tcp_handshake(node.host, node.port, timeout=5) и marzban_node_status == "connected"
    если ok:
        fail_count = 0; status = healthy
    иначе:
        fail_count += 1
        если fail_count >= 3 и status != degraded:
            status = degraded
            запустить план восстановления:
                шаг 1: сменить SNI на следующий из пула  → проверить
                шаг 2: сменить порт на резервный          → проверить
                шаг 3: сделать Hysteria2 основным         → проверить
                шаг 4: перевести пользователей на запасную ноду локации
            при успехе: записать health_event, уведомить пользователей и админа
            при неудаче всех шагов: алерт админу «нужен новый IP»
```

Состояние нод и счётчики — в таблице `nodes` + быстрый кэш в Redis.
История инцидентов — в `health_events` (нужна, чтобы видеть, какая нода «сыпется»).

## 6. Масштабирование до 1000+ пользователей

| Узкое место | Когда наступит | Решение |
|---|---|---|
| Rate-limit Telegram (30 msg/s) | Рассылка на 1000 юзеров | Очередь рассылки с троттлингом 20 msg/s |
| Соединения к Postgres | ~200 одновременных | Пул SQLAlchemy 20 + pgbouncer при росте |
| Трафик ноды | ~300 юзеров на 1 Гбит | Добавить ноду в ту же локацию, балансировка по загрузке |
| Опрос Marzban | 1000 юзеров × статусы | Кэш профилей в Redis (TTL 60 с) + батч-запросы |

Добавление ноды = запуск `scripts/install-node.sh` на новом VPS + одна запись в
таблице `nodes`. Код менять не нужно.

## 7. Почему именно этот стек

- **aiogram 3** — единственная зрелая асинхронная библиотека для Telegram на Python
  с нормальным роутингом, FSM и поддержкой Mini App/Stars.
- **FastAPI** — вебхуки платежей и Mini App API в одном процессе, автодокументация
  `/docs`, та же async-модель, что и у бота.
- **Marzban** — готовое управление Xray с REST API, нодами и подписками; писать своё
  управление Xray для v1.0 — месяц работы без выигрыша.
- **PostgreSQL** — деньги требуют транзакций и целостности; SQLite при вебхуках
  и конкурентных платежах даёт блокировки.
- **Redis** — FSM бота, антифрод-метки с TTL и кэш; без него каждое нажатие кнопки
  бьёт в Postgres.
